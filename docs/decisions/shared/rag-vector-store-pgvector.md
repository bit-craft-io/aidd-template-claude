# RAG のベクトル保存先に PostgreSQL(pgvector)を採る

## 背景・課題

`docs/` の知識を、ツール呼出で引ける RAG を、ひな形の標準機能として作る。
ベクトルの保存先を、PostgreSQL(pgvector)にするか、ベクトル検索の専用 DB(Qdrant など)にするかを、決める必要が生じた。
開発では Docker のコンテナで動かし、将来は Google Cloud・AWS へ載せる見込みである。

## 決定

ベクトルの保存先は、PostgreSQL(pgvector)とする。
開発は Docker のコンテナ、将来は Google Cloud・AWS の管理 PostgreSQL に載せ替える。接続先は、環境変数で差し替える。

## 検討した代替案

- Qdrant: ベクトル検索の専用 DB で、導入が軽い。
  採らなかった理由: Google Cloud・AWS のクラウド標準の管理サービスに、直接の提供が無い(Qdrant 社の管理サービスはある)。将来、本番へ載せるときの選択肢が、限られる。

## 影響・トレードオフ

- 引き受ける不利益:
  - テーブル設計・索引・SQL を、自分で書く手間が増える
  - 検索の入口(MCP など)は、別に用意する必要がある
  - 件数が大きく増えたとき、索引の調整が要る
- 得るもの:
  - Google Cloud(Cloud SQL・AlloyDB)、AWS(RDS・Aurora)の管理サービスへ、載せ替えやすい(各対応は、未確認)
  - 全文検索との組み合わせなど、SQL で制御できる
- 見直す兆候: 件数・負荷が増え、pgvector の性能が足りなくなったとき
