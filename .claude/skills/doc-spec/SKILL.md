## いつ書くか

- ある程度まとまった機能・インフラ単位の実装に着手する前
- 実装方針が頭の中で漠然としており、書き出して整理したい時
- 実装方針を先に人間へ共有し、早期にフィードバックを得たい時

## いつ書かぬか

- 数行程度の自明な修正、バグ一件の修正等、書き出すまでもない軽微な作業
- 既にdoc-specが存在する機能への追加実装(既存のdoc-specを更新すれば足りる)

## 書き方

1. `docs/templates/doc-spec-template.md` を複製する(置き場所は対象プロ
   ジェクトの慣習に合わせる。例: `docs/design/<機能名>.md`)
2. **考えながら書く。清書を目指さない。** 書き殴った内容がそのまま後で共有
   できる、という前提を活かす
3. 書く過程で「これは他の案もあり得る、判断が分かれる」決定に行き当たった
   ら、その部分だけ `docs/templates/adr-template.md` を使いADRとして切り出
   す。doc-spec自体には全てを決定事項として書き込まない
4. 書き終えたら人間と共有し、フィードバックを受けて更新する

## ADRとの違い

| | doc-spec | ADR |
|---|---|---|
| 対象 | 機能・インフラ単位の全体像 | 個別の分岐点における決定 |
| タイミング | 実装着手"前"、考えを整理する段階 | 判断が固まった時点 |
| 粒度 | 一機能に一つ程度 | 一機能に複数生じ得る、または一つも生じぬこともある |
| 更新 | 実装が進むにつれ書き足して良い | 採用後は書き換えず、覆す場合は新規ADR |
