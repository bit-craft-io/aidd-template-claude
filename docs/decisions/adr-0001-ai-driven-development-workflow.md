# ADR-0001: AI駆動開発における意思決定フロー

## ステータス

提案中

## 背景・課題

本リポジトリでは複数プロジェクトを `projects/<name>/` 配下に束ね、Claude Codeを実装の主体的な担い手として活用していく。その進め方には大きく二通りある。

1. 実装を先に進め、結果が出てからその内容をドキュメント化する(いわゆる「バイブコーディング」)
2. 決定事項を先にADRとして固定し、その制約の中でClaudeに実装させる(「AI駆動開発」)

①は着手の速さでは勝るが、AIはその場の文脈のみで判断を下すため、セッションを跨ぐと判断根拠が失われ、同種の決定が都度ブレる恐れがある。特に複数プロジェクト・複数セッションに跨って一貫性を保ちたい場合、①では歯止めが効かぬ。

## 決定

本リポジトリにおけるAI駆動開発は、次の順序で進める。

1. 実装着手前に、ADR(`docs/decisions/adr-template.md` を複製)をドラフト(ステータス: 提案中)として起票する
2. 人間とClaudeとの対話でドラフトを詳細化し、背景・代替案・トレードオフを埋める
3. 内容が固まった時点でステータスを「採用」に変更する
4. **採用後のADRは内容を直接書き換えない。** 判断を覆す場合は新規ADR(`adr-000X`)を起こし、旧ADRのステータスのみ「廃止(後継: ADR-000X)」に変更する
5. 以降Claudeへの実装指示は、採用済みADRの内容を前提として行う。指示がADRと矛盾する場合、Claude側からその矛盾を指摘する

適用対象は「後から判断根拠を疑われそうな決定」(技術選定、構成の転換、複数案からの選択)に限る。自明な実装細部にまでADRを起こす必要はない。

## 検討した代替案

- **①実装後にドキュメント化(バイブコーディング的進め方)** — 採らず。判断の一貫性を事後的にしか担保できず、AIへの指示の再現性が保てないため
- **ADRを設けずCLAUDE.mdを都度直接更新** — 採らず。検討過程・却下案の記録が失われ、後から「何故そう決めたか」を追えなくなるため

## 影響・トレードオフ

- 実装着手前に一手間(ADR起票)が増える。軽微な変更にまで適用すると運用が重くなるため、適用対象の線引きは都度見直しが要る
- 「採用」後は直接編集不可とすることで、なし崩し的な仕様変更に意図的な摩擦を課す。これは硬直化のリスクと表裏一体であり、頻繁に覆るようであれば運用自体の見直しが必要
