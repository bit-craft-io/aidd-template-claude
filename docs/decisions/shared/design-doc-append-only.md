# 承認後の設計書は追記のみとする

> **遡及作成(2026-10-08)**: 本書は、決定の後に、履歴とルールの本文から書き起こした。当時の検討過程は記録に残っておらず、判断の理由のうち出典で確認できないものは「要確認」と記す。

## 背景・課題

会話ベースの開発では、仕様の変更や、仕様漏れの補いが、会話の中で決まる。これをリポジトリに残さないと、設計書を読んでも今の仕様が分からなくなる(出典: `.claude/rules/record-decisions.md`)。

承認済みの設計書を直接書き換えると、何を合意したかが追えなくなる点も、同ルールの「元の本文は、合意した内容」から読み取れる。ただし、書き換えを避ける理由として明記されているわけではない(要確認)。

## 決定

- 承認(合意)後の設計書は、元の本文を書き換えず、末尾への追記で対応する
- 設計書の先頭に「追記の一覧」の節を置き、追記のたびに1行足す
- 元の記述と食い違う追記は、どの記述をどう変更するかを追記の節に書く。元の本文に注記は付けない
- 承認の前の設計書は、直してよい
- 実装の不具合(仕様どおりでない)は設計書を変えず、直す手順を計画書に書く

要確認(記録なし)。

## 影響・トレードオフ

- 設計書が追記で長くなる。今の仕様は、元の本文と追記を合わせて読む必要がある
- 見た目の微調整は残さない、と対象を絞っている。線引きは都度見直しが要る
