# RAG の埋め込みは、自前のモデルで動かし、外部の API に送らない

## 背景・課題

`docs/` の知識(社内のナレッジ)を、RAG にする。取り込みでは、全ての断片が、埋め込みの処理を通る。
埋め込みを外部の API で行うと、全ての断片が外部へ送られる。この形が、閉じた環境での、社内のナレッジの利用と合うかが問題になった。

## 決定

埋め込みは、自前のモデルを、手元(開発)と自社のクラウド内(本番)の、自社の管理下のコンテナで動かす。
外部の埋め込み API には、断片を送らない。

(この決定の対象は、埋め込みのみ。回答側の LLM(Claude Code)の経路は、対象外)

## 検討した代替案

- 外部の埋め込み API(クラウド事業者・他社のサービス): 導入が軽く、精度が高い傾向がある。
  採らなかった理由: 全ての断片が、外部へ送られ、閉じた環境での利用と合わない。
- クラウド事業者の埋め込みサービスを、自社の契約・プロジェクトの下で使う: 契約の条件次第で、許容されうる。
  採らなかった理由: 契約と社内規程の確認が要る(要確認)。当面は、採らない。

## 影響・トレードオフ

- 引き受ける不利益:
  - 日本語に強いモデルの選定と、実行基盤(Ollama など)の運用が要る
  - 本番のクラウドにも、埋め込み用のコンテナを置く必要がある
  - 精度が、外部の大きなモデルに劣りうる
  - 外部 API 前提で作った、既存の表や流れがある場合は、次元の違いにより、作り直しが要る
- 得るもの:
  - 全ての断片が、外へ出ない
  - 同じモデルを、手元と本番で動かせば、ベクトルが揃う
- 見直す兆候:
  - 評価用の質問集で、精度が基準に届かないとき
  - 社内規程が、外部 API の利用を許すとき
  - モデルを変えるときは、全件の取り直しが要る
