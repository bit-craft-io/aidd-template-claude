# git

git のコミット・push・プルリクエスト(PR)の作成を、手順どおりに行う。何を守るか(ブランチの運用、頼まれたときだけ行う、メッセージの形)は、`.claude/rules/git.md` と `base-rules.md` に従う。ここには、手順だけを書く。同じ内容を、規則とこのファイルの両方に書かない。

## 操作の一覧

- `commit`(`コミット`): 変更を確かめ、コミットする
- `push`(`プッシュ`): ブランチを、`origin` に push する
- `pr`(`プルリクエスト`): `develop` 向けの PR を作る

書式は、`/git <操作>`。操作名は、英語でも、日本語でも、よい。ユーザーが明示したときだけ、動く。

## 共通の決まり

- **実行の前に、対象を見せて、確認を取る**: コミットのファイルとメッセージ、push のブランチとコミット、PR の題と本文。確認が無いうちは、変更も、外への送信も、しない
- 操作のたびに、結果(いまのブランチ、先頭のコミット、`git status`)を確かめて、報告する。失敗したのに、続けない
- 失敗の原因が分からないときは、止めて、報告する。`--no-verify` で、検査を飛ばさない。`--force` で、上書きしない。`reset --hard`・`clean -f` など、変更を捨てる操作は、頼まれても、確認してから行う
- ユーザーの変更を、勝手に捨てない。無関係の変更は、そのまま残す

## commit

1. **状況を示す**: `git branch --show-current`、`git status --short`、`git diff --stat`。ブランチが `main` のときは、止める(直接コミットしない)。`develop` のときも、止めて、聞く(作業は、その日の `feature/YYYYMMDD` で行う)
2. **対象のファイルを決める**: ユーザーが指定すれば、それに従う。指定が無ければ、案を出す。次は、含めない。
   - 目的が違う変更(1つのコミットに、1つの目的。設計書・計画書の変更は、実装と分ける)
   - 鍵・`.env`・トークンなどの秘密
   - 自分が作っていない、無関係の変更
3. **メッセージの案を作る**: 形は、`type(scope): 要約 (チケットのキー)`。`type` は、`feat` / `fix` / `docs` / `style` / `test` など。チケットに結びつかないときは、キーを省く。過去のコミットの題(`git log --oneline -10`)と、言い回しを合わせる。末尾の2行(共著者、セッション)は、Claude Code が指示する形に従う。題と末尾の間は、空行を入れる
4. **確認を取る**: ファイル、メッセージを見せる
5. **コミットする**: `git add <ファイルを、1つずつ指定>`(`git add -A`・`git add .` は、使わない)。`git commit`
6. **報告する**: コミットの SHA と題、残っている未コミットの変更。検査(pre-commit)で失敗したときは、原因を直し、**新しい**コミットを作る(`--amend` は、頼まれたときだけ)

## push

1. **状況を示す**: ブランチ、`origin` との関係(`git fetch` のあと、`git rev-list --left-right --count origin/<ブランチ>...HEAD`。初回は、上流が無い)、基点(`develop`)に対して、遅れているか
2. **止める場合**: ブランチが `main` のとき。ブランチが、`develop` のとき(聞く)。未コミットの変更があるとき(コミットするか、残してよいかを聞く)
3. **確認を取る**: 送る先(`origin`、ブランチ名)と、送るコミットの一覧(`git log --oneline origin/<ブランチ>..HEAD`。初回は、`origin/develop..HEAD`)を見せる
4. **push する**: 初回は `git push -u origin <ブランチ>`。2回目以降は、`git push`
5. **報告する**: 結果(送ったコミット、先頭の SHA)。拒否されたときは、原因を報告する。`pull`・`rebase` は、頼まれたときだけ行う

## pr

1. **作る手段を確かめる**: 次の順で、使えるものを探す。
   - GitHub のコネクタ(`mcp__*github*` のツール)が、この会話にあれば、それを使う
   - 無ければ、`gh auth status` で、`gh` が、ログイン済みか確かめる
   - どちらも無いときは、題と本文の案だけを出し、手作業で作る手順(GitHub の画面)を、示して、終わる。ログインは、ユーザーが行う(`! gh auth login`)
2. **前提を確かめる**: ブランチが、`origin` に push 済みで、ローカルと同じであること。違えば、「先に `/git push`」と案内し、止める。ブランチが `main`・`develop` のときも、止める
3. **基点と差分を調べる**: 基点は、`develop`(指定が無いとき)。`git log --oneline origin/develop..HEAD`、`git diff --stat origin/develop...HEAD`。基点より、遅れている・枝分かれしているときは、知らせて、聞く
4. **題と本文の案を作る**: 事実だけを書く。コミット、チケットのキー、確認した結果(会話に出たもの)から作り、作文しない。確かめていないことは、「未確認」と書く。
   - 題: 内容を表す短い文(コミットの題と、言い回しを合わせる)
   - 本文: 次の4項目。
     - `## 要約`: 何を、なぜ、変えたか
     - `## 関連チケット`: Jira のキー(例: AIDDK-2、AIDDK-3)
     - `## 確認した内容`: テスト、実機の確認、できなかった確認
     - `## 注意点`: DB の作り直し、環境変数の追加、マージ後の作業など。無ければ、「なし」
   - 末尾は、Claude Code が指示する形(PR の説明の、末尾の行)に従う
5. **確認を取る**: 基点、題、本文を見せる
6. **PR を作る**: 手順 1 で決めた手段で、`develop` 向けに作る。ドラフトにするかは、ユーザーの指示に従う(指示が無ければ、通常)
7. **報告する**: PR の URL、題。マージは、行わない(ユーザーが行う)

## やらないこと

- ユーザーが、明示していないのに、起動しない(自分の判断で、コミット・push・PR を作らない)
- マージ(PR のマージを含む)。`main` への push・コミット
- `--force`・`--no-verify`・`reset --hard` などを、確認なしに使うこと
- 確認を取る前に、変更や外への送信を行うこと
- 鍵・トークン・`.env` を、コミット・PR の本文に入れること
