# ADR(判断の記録)

判断が分かれる点で、問うて、決まった結果を、ADR(`docs/decisions/`)に残す。あとから、「なぜそう決めたか」を、追える状態を保つ(再現性のため)。

## 起こす場面

- 判断が分かれる点(技術選定、構成の転換、複数案からの選択)に行き当たったとき
- 起こさないもの: 見た目の微調整、自明な実装細部
- 仕様の変更や漏れの補いは、ADR でなく、設計書の追記(`record-decisions.md`)に書く。判断の分かれ目と、採らなかった案は、ADR に書く

## 進め方

1. Claude が、案を示して、ユーザーに問う
2. ユーザーが決めたら、Claude が、直後に、ADR の下書きを出す。ユーザーに黙って、書き進めない
3. 下書きは、`docs/templates/adr-template.md` を複製して、`docs/decisions/` の直下に作る。番号は、直下の ADR の連番+1(`shared/` は数えない)。ステータスは「提案中」
4. 「採用」への変更は、ユーザーが確かめたあとに行う

## 書き方

- 書くのは、判断の理由、採らなかった案、引き受ける不利益。「何を、どうするか」の仕様は、設計書に有るので、書き写さず、リンクで指す
- 採用後の ADR は、書き換えない。覆すときは、新しい ADR を起こし、旧 ADR のステータスだけを「廃止(後継: ADR-XXXX)」に変える。採用の前は、直してよい
- 同じ内容を、設計書と ADR の両方に書かない

## 遡及して作るとき(決定のあとに書き起こす場合)

- 冒頭に、「遡及作成(日付)」と明記する
- 末尾に、出典(設計書の節、計画書、コミット)を付ける
- 出典で確認できない理由や、採らなかった案は、作文せず、「要確認」と書く

## 共通の決定(`docs/decisions/shared/`)

- ひな形から引き継いだ、全プロジェクト共通の決定を置く。番号は付けない
- 直下の ADR(プロジェクト固有)と違い、書き換えてよい
