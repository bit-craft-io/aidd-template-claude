# git の運用

ブランチ運用の基本(その日の日付の `feature/YYYYMMDD` で作業する、`develop` から作る、`main` に直接コミットしない)は、`base-rules.md` の「ブランチ運用」に従う。ここには、それに無い規則を書く。

## ブランチの切り替え

- 前の日の `feature/YYYYMMDD` に、未マージの作業があるときは、先に、PR で `develop` へマージする(マージは、ユーザーが行う)。そのあとで、`develop` を更新し、今日のブランチを、そこから作る
- 未コミットの変更があるときは、ブランチを切り替える前に、コミットする(または、ユーザーに、扱いを確認する)。切り替えが中断したまま、続く操作が、別のブランチの上で走るのを避けるため
- ブランチを作る、切り替える、更新するときは、実行のたびに、結果(いまのブランチ、先頭のコミット)を確かめる。失敗したのに、続けない

## コミット・push・マージ

- コミット・push・PR の作成・マージは、ユーザーが頼んだときだけ行う。ただし、`jira-exec` の計画の流れで、了承された計画書に、コミットの手順が書かれているときは、その範囲のコミットは、行ってよい
- PR のマージは、ユーザーが行う
- ブランチの位置を動かす操作(`git branch -f`、`reset`、`rebase` など)は、ユーザーが頼んだとき、または、直前の自分の操作を元に戻すときだけ。元に戻したときは、報告する

## コミットメッセージ

- 形: `type(scope): 要約 (チケットのキー)`。`type` は `feat` / `fix` / `docs` など。チケットに結びつかないときは、キーを省く
- 末尾の行は、Claude Code が指示する形(共著者と、セッションの行)を付ける
- 1つのコミットに、1つの目的を入れる。設計書・計画書の変更は、実装のコミットと、分ける(同じ内容を、あとで追える形にするため)
